# Web 生图平台 MVP 设计

Date: 2026-05-02

## 目标

把当前本地/桌面优先的生图工具，扩展为一个面向普通用户的网页平台 MVP。

平台需要支持两种使用方式：

- 自有 API key 模式：用户自行填写 `Base URL`、`API key`、模型名，在网页内完成生成。第一版优先把配置和结果保存在用户浏览器本地，尽量不占用平台存储。
- 平台托管 key 模式：用户注册登录后直接体验生图，不需要理解 API key。平台使用管理员配置的供应商、模型和 API key 池统一调用，并通过额度、队列、熔断和监控控制成本。

MVP 的重点不是一次性做完整商业平台，而是先跑通“注册 -> 免费体验 -> 模板辅助生成 -> 供应商保护 -> 手动充值 -> 管理员加额度”的闭环。

## 当前项目状态

当前仓库是 Vite + React + Tauri 项目，已经具备：

- 文生图与图生图调用。
- OpenAI 兼容接口请求构造。
- 图片输出参数配置。
- 多参考图上传。
- 本地/桌面配置保存。
- 本地图片保存与历史记录。
- Windows 安装包链路。

当前仓库不具备：

- 后端 API。
- 用户账号。
- 数据库。
- 任务队列。
- 平台托管 API key 管理。
- 额度和支付。
- 管理后台。
- 服务健康监控。

因此 Web 平台 MVP 应该作为新的 Web 服务架构来设计，而不是继续把账号、支付和队列塞进 Tauri 桌面应用。

## MVP 范围

第一版包含：

- 网页生图工作台。
- 邮箱验证码注册和登录。
- 自有 API key 模式。
- 平台托管 key 模式。
- 每个新用户每日 1 张免费体验额度。
- 管理员手动给用户增加额度。
- 微信二维码手动支付流程。
- 提示词模板库。
- 生成任务队列。
- 供应商级熔断保护。
- API key 池动态分配。
- 管理后台基础页面。
- 生图服务状态展示。

第一版不包含：

- 自动微信支付回调。
- 复杂会员系统。
- 社区模板市场。
- 自动从 GitHub 大规模抓取并上线模板。
- 多供应商自动切换。
- 手机 App。
- 公共图片广场。
- 长期图片云盘。

## 推荐架构

采用 monorepo 结构，保留当前桌面应用，同时新增 Web 平台模块：

```text
apps/
  web/       React 网页端
  api/       后端 API，负责账号、额度、模板、订单、任务创建
  worker/    生图队列消费者，负责供应商调用、熔断、结果保存
packages/
  core/      共享逻辑：模型参数、错误分类、提示词工具、响应解析
```

推荐技术栈：

- 前端：React。
- 后端：Fastify 或 NestJS。
- 数据库：PostgreSQL。
- 队列：Redis + BullMQ。
- 反向代理：Nginx。
- 部署：Linux 轻量服务器。
- 文件存储：MVP 可先用服务器本地磁盘，后续迁移到对象存储。

如果先部署在 4 核 4G 服务器，并且只给本项目约 50% 资源，应按 2 核 2G 预算设计。真正瓶颈主要是供应商耗时、并发限制和调用成本，不是 CPU。

## 用户模式

### 自有 API key 模式

目标用户是懂一点 API 配置的用户。

行为：

1. 用户进入网页。
2. 选择自有 API key 模式。
3. 填写 `Base URL`、`API key`、文字模型、图片模型。
4. 选择提示词模板或手写提示词。
5. 发起生成。
6. 图片默认保存到浏览器本地或下载到用户电脑。

存储规则：

- 配置默认保存在浏览器本地。
- 自有 API key 不写入平台数据库。
- 自有 API key 模式下的图片默认不上传平台长期存储。
- 如果浏览器不能直接调用用户供应商，后端可提供临时代理，但代理不持久化用户 key。

限制：

- 临时代理会消耗平台带宽和服务器资源。
- 以后可对临时代理设置免费次数或收费。
- 如果用户供应商返回高风险错误，平台只在该用户本地配置维度提示，不影响平台托管服务状态。

### 平台托管 key 模式

目标用户是完全不懂 API key 的普通用户。

行为：

1. 用户注册登录。
2. 用户获得每日免费体验额度。
3. 用户选择模板或输入提示词。
4. 后端检查用户额度和供应商状态。
5. 任务进入队列。
6. worker 从管理员配置的 API key 池中选择一个 key 调用供应商。
7. 成功后保存图片并扣额度。
8. 失败时按错误类型处理。高风险供应商错误不扣用户额度，但记录平台成本风险。

## 供应商级熔断保护

管理员会提供 10 个 API key。它们属于同一个 `Base URL`，因此需要按供应商维度处理健康状态。

硬规则：

- 同一个 `Base URL + imageModel` 下，一个 key 的高风险失败代表供应商模型可能异常。
- 健康检查每次只允许使用 1 个 key。
- 如果健康检查 key 返回高风险失败，立即打开供应商级熔断。
- 供应商熔断后，不再测试其他 9 个 key。
- 普通用户请求中，任意 key 出现高风险失败，也立即打开供应商级熔断。
- 熔断期间，普通用户不能触发平台托管生图调用。
- 熔断期间，管理员可手动发起一次探测。
- 高风险失败不扣用户额度。
- 平台仍需记录这次失败可能已经产生供应商成本。

高风险错误包括：

- HTTP `524`。
- 响应中包含 `openai_error`。
- 响应中包含 `bad_response_status_code`。
- 响应中没有任何图片数据。
- 供应商返回 200 但 payload 中包含结构化错误。

默认熔断参数：

```text
供应商熔断时长：5 分钟
高风险失败阈值：1 次即可打开熔断
管理员手动探测：允许
普通用户熔断期间调用：禁止
```

选择 1 次即熔断，是因为该类错误可能已经产生费用，继续调用会放大损失。

## API key 动态分配

key 动态分配只在供应商状态健康时发生。

每个 key 维护状态：

```text
enabled
state: healthy | cooldown | disabled
cooldownUntil
inFlight
maxInFlight
success15m
fail15m
costRiskFail15m
rateLimit15m
success1h
fail1h
consecutiveFailures
consecutiveCostRiskFailures
ewmaLatencyMs
lastUsedAt
```

选择流程：

1. 先检查 `Base URL + imageModel` 供应商状态。
2. 如果供应商熔断，直接拒绝任务。
3. 过滤禁用、冷却中、并发已满的 key。
4. 对候选 key 评分。
5. 使用加权随机选择 key。
6. 记录 `selectedApiKeyId` 到任务。
7. 调用结束后更新 key 和供应商状态。

评分因素：

- 最近 15 分钟成功率越高，分数越高。
- 当前 `inFlight` 越高，分数越低。
- 最近 429 越多，分数越低。
- 最近高风险失败会使 key 冷却，并触发供应商熔断。
- 延迟越高，分数越低。
- 最近使用过多的 key 略微降权。
- 太久没用的健康 key 给少量探索权重。

伪代码：

```ts
function pickApiKey(keys, provider, now) {
  if (provider.state === "open" && provider.openUntil > now) {
    throw new ProviderCircuitOpenError();
  }

  const candidates = keys.filter((key) =>
    key.enabled
    && key.state !== "disabled"
    && (!key.cooldownUntil || key.cooldownUntil <= now)
    && key.inFlight < key.maxInFlight
  );

  const scored = candidates
    .map((key) => ({ key, score: scoreApiKey(key, now) }))
    .filter((item) => item.score > 0);

  if (scored.length === 0) {
    throw new NoAvailableApiKeyError();
  }

  return weightedRandom(scored);
}
```

结果处理：

- 成功：清空连续失败计数，更新成功率和延迟。
- 401/403：禁用该 key。
- 429：该 key 冷却 2 分钟，不触发供应商级熔断。
- 524/openai_error/bad_response_status_code：该 key 冷却，同时打开供应商级熔断。
- 网络超时：普通失败，连续失败达到阈值后 key 冷却。

## 健康检查

健康检查用于展示平台服务状态，也用于自动从熔断中恢复。

规则：

- 每次健康检查只使用 1 个 probe key。
- probe key 从健康 key 中按低使用量优先选择。
- 如果当前供应商已熔断，定时健康检查不自动连续探测，避免重复成本。
- 供应商熔断到期后，进入 `half_open` 状态。
- `half_open` 状态只允许 1 个探测任务。
- 探测成功后恢复健康。
- 探测失败后重新打开熔断。

默认频率：

```text
白天：每 60 分钟一次
夜间：每 120 分钟一次
供应商已熔断：等待熔断到期后最多探测 1 次
```

管理员可配置：

- 白天开始和结束时间。
- 白天检查间隔。
- 夜间检查间隔。
- 熔断时长。
- 是否启用自动探测恢复。

图片健康判断：

- 响应必须包含可解析图片数据。
- 如果平台会保存测试图，图片文件大小应大于 500KB 才算健康。
- 如果模型或供应商在某些参数下生成小图，应允许管理员调整最小文件大小阈值。

## 生成任务队列

平台托管模式下，所有生成请求都必须进入队列。

默认限制：

```text
平台总生图并发：2
单 key 并发：1
单用户同时排队任务：1
单任务超时：240 秒
队列等待超时：10 分钟
```

任务状态：

```text
queued
running
succeeded
failed
cancelled
provider_circuit_open
```

失败扣费规则：

- 生成成功：扣用户额度。
- 用户输入违规或参数错误：不调用供应商，不扣额度。
- 供应商高风险失败：不扣用户额度。
- 用户取消排队任务：不扣额度。
- 任务开始调用供应商后取消：第一版不提供取消，避免状态复杂。

## 额度系统

额度用账本模型，不直接只存一个数字。

账本事件：

```text
daily_free_grant
admin_adjustment
manual_payment_credit
generation_debit
generation_refund
provider_failure_no_charge
```

规则：

- 新用户每天获得 1 张免费体验额度。
- 免费体验额度可设置每日过期。
- 平台托管生成成功才扣额度。
- 高风险供应商失败不扣额度，但写入成本风险日志。
- 管理员可手动给用户加额度。

## 支付 MVP

第一版采用微信二维码手动充值。

流程：

1. 用户选择固定金额：5 元、10 元。
2. 页面展示微信收款码。
3. 用户付款后提交付款备注或截图。
4. 后台生成待审核订单。
5. 管理员确认到账。
6. 系统给用户增加额度。

第一版不做自动到账，因为微信个人收款码没有稳定的官方回调能力。手动审核更慢，但实现成本低，也更适合早期验证。

## 注册与防滥用

注册方式：

- 邮箱验证码登录/注册。

限制：

- 同 IP 每小时最多发送 5 次验证码。
- 同邮箱每天最多发送 5 次验证码。
- 同 IP 每天最多注册 3 个账号。
- 验证码 10 分钟有效。
- 验证码错误 5 次后短时间锁定。
- 禁止常见一次性邮箱域名。
- 可接入 Turnstile 或 hCaptcha。

生成限制：

- 未登录用户不能使用平台托管 key。
- 新用户每日免费体验 1 张。
- 同用户同时只能有 1 个平台托管任务。
- 同 IP 平台托管任务频率限制。
- 管理员可禁用用户。

## 提示词模板库

模板库第一版做精选，不做海量自动导入。

模板字段：

```ts
type PromptTemplate = {
  id: string;
  category: "portrait" | "graduation" | "product" | "poster" | "avatar" | "scene";
  title: string;
  description: string;
  prompt: string;
  variables: Array<{
    key: string;
    label: string;
    placeholder: string;
    required: boolean;
  }>;
  sourceUrl?: string;
  license?: string;
  enabled: boolean;
};
```

模板使用方式：

1. 用户选择分类。
2. 用户选择模板标题。
3. 页面展示少量变量输入框。
4. 系统把变量填入完整提示词。
5. 用户可编辑最终提示词。
6. 用户点击生成。

模板来源要求：

- 记录来源链接。
- 记录许可证。
- 无明确许可证的模板不直接批量上线。
- 可以人工改写为自有模板，但需要避免复制大段受限内容。

## 管理后台

第一版后台页面：

- 用户列表：搜索、禁用、查看额度、手动加额度。
- 订单列表：查看待审核付款，确认加额度。
- 模板管理：新增、编辑、启用、禁用模板。
- 供应商状态：查看熔断状态、最近错误、手动解除熔断、手动探测。
- API key 管理：新增 key、禁用 key、查看最近成功率和并发。
- 任务日志：查看生成任务、错误、耗时、是否扣额度。

管理员操作写入审计日志。

```text
正常
```

## 存储策略

自有 API key 模式：

- 默认不占用平台存储。
- 图片由浏览器下载或保存到用户本地。

平台托管 key 模式：

- MVP 可以先把图片保存到服务器本地磁盘。
- 图片保留期默认 7 天。
- 用户可下载图片。
- 后续迁移到对象存储。

## 部署与容量

按 4 核 4G 服务器但只给本项目 50% 资源估算，MVP 应按 2 核 2G 设计。

建议部署：

```text
Nginx
Web 静态资源
API 服务
Worker 服务
PostgreSQL
Redis
```

起步并发：

```text
平台托管生图总并发：2
单 key 并发：1
API 服务实例：1
Worker 实例：1
```

容量判断：

- 自有 API key 模式主要消耗网页和少量代理资源，可支持较多访问。
- 平台托管 key 模式主要受供应商耗时和成本限制。
- 如果每张图 120 秒，总并发 2，理论约 60 张/小时。
- 按 0.1 元/张，持续满载成本约 6 元/小时。
- 早期不应追求高并发，应优先保护成本和服务稳定。

## 错误处理

错误分类：

- 用户输入错误：前端或 API 拒绝，不进入队列。
- 认证错误：禁用 key 或提示用户自有 key 配置错误。
- 限流错误：key 冷却。
- 高风险供应商错误：供应商级熔断。
- 网络超时：普通失败，达到阈值后 key 冷却。
- 响应无图：高风险供应商错误。

用户文案：

- 不暴露内部 key。
- 不显示供应商原始敏感信息。
- 明确说明是否扣额度。
- 供应商异常时提示稍后再试。

## 安全要求

- 平台托管 API key 只保存在服务端。
- API key 加密存储。
- 日志中不打印完整 key。
- 管理后台需要管理员登录。
- 管理员操作写审计日志。
- 用户自有 key 默认只存在浏览器本地。
- 后端代理自有 key 请求时不持久化 key。

单元测试：

- 错误分类。
- 供应商级熔断判断。
- key 评分和选择。
- 额度扣减与失败不扣费。
- 模板变量填充。
- 邮箱验证码限流。

集成测试：

- 注册登录。
- 每日免费额度发放。
- 生成任务入队。
- worker 成功生成并扣额度。
- 524 错误触发供应商熔断。
- 熔断后不再尝试其他 9 个 key。
- 管理员手动加额度。
- 手动支付审核。

手动验收：

- 新用户注册后可免费生成 1 张。
- 供应商异常时用户不能继续平台托管生成。
- 自有 API key 模式不占用平台额度。
- 模板能按变量生成可编辑提示词。
- 管理员能查看任务和错误。

## 分期实施

### Phase 1：Web 平台骨架

- 建立 Web/API/Worker 基础结构。
- 接入 PostgreSQL 和 Redis。
- 建立用户表、模板表、任务表、额度账本表。
- 实现邮箱验证码登录。

### Phase 2：平台托管生图闭环

- 实现生成任务队列。
- 实现 API key 池。
- 实现供应商级熔断。
- 实现生成成功扣额度。
- 实现失败不扣额度。

### Phase 3：模板库和自有 key 模式

- 建立模板管理。
- 前台模板选择与变量填写。
- 自有 API key 模式本地配置。
- 自有 key 直连或临时代理。

### Phase 4：支付和后台

- 微信二维码手动充值。
- 管理员审核订单。
- 管理员手动加额度。
- 任务日志和供应商状态后台。

### Phase 5：稳定性增强

- 服务状态页。
- 定时健康检查。
- 管理员手动探测。
- 图片保留策略。
- 监控和告警。

## 成功标准

MVP 完成时，应满足：

- 普通用户可以邮箱注册并完成一次免费体验。
- 平台托管 key 模式下，用户无需理解 API key。
- 供应商出现 524/openai_error 时，平台会立即暂停该供应商模型调用。
- 供应商异常不会导致系统继续消耗其他 9 个 key 的测试成本。
- 用户可通过模板快速生成提示词。
- 管理员可以手动审核充值并加额度。
- 管理员可以查看供应商状态、任务日志和 key 状态。
- 自有 API key 用户可以不占用平台额度使用网页工具。
