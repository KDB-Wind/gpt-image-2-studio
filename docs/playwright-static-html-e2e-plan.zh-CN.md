# 静态 HTML 版 Playwright 全流程测试计划

> **历史材料：** 本文已被 2026-07-11 独立审计与修复取代，仅保留用于追溯，不代表当前验证结论。

本计划用于验证 GitHub Pages 静态页面和单文件 HTML 版的真实用户流程。目标是先发现问题、记录严重级别和复现步骤；本阶段不做功能修复。

## 1. 测试目标

- 验证用户首次打开页面后，能否完成配置、连通性测试、单图生成、批量生成、历史回看和版本切换。
- 重点验证“保存目录授权后是否真正生效”，避免图片仍落到浏览器默认下载目录。
- 验证文字模型规划批量任务、批量失败重试、暂停继续、历史批次展开等复杂流程。
- 验证图生图入口在供应商支持或不支持时的行为是否清晰、可恢复。
- 输出一份缺陷清单，按 P0/P1/P2/P3 分级，供下一阶段修复。

## 2. 安全要求

- 不把真实 `API key` 写入源码、README、测试文档、截图文件名、日志文件或 Git 提交。
- 测试配置通过环境变量传入：

```powershell
$env:E2E_BASE_URL="https://your-provider.example/step_plan"
$env:E2E_API_KEY="YOUR_API_KEY"
$env:E2E_TEXT_MODEL="your-text-model"
$env:E2E_IMAGE_MODEL="your-image-model"
```

- Playwright 测试报告、trace、截图中如果出现设置页，需要检查是否暴露完整密钥；必要时只保存局部截图或脱敏截图。
- 测试结束后运行密钥扫描：

```powershell
rg -n "sk-[A-Za-z0-9_-]{24,}|KNOWN_REAL_KEY_PREFIX|YOUR_REAL_KEY" . --glob "!node_modules/**" --glob "!dist/**"
```

## 3. 测试环境

- 工作目录：`D:\DemoProject\chatToImage\.worktrees\public-lite-cleanup`
- 本地预览：优先使用 `npm run build:static` 后的静态预览。
- 浏览器：Chromium / Edge 优先，因为保存目录依赖 File System Access API。
- 真实供应商配置：
  - `Base URL`：从 `E2E_BASE_URL` 读取。
  - `API key`：从 `E2E_API_KEY` 读取。
  - 文字模型：从 `E2E_TEXT_MODEL` 读取。
  - 生图模型：从 `E2E_IMAGE_MODEL` 读取。

## 4. 推荐执行命令

```powershell
npm run build:static
npm run site:check
npm exec -- vite preview --config vite.static.config.ts --host 127.0.0.1 --port 4174 --strictPort
```

如果后续新增 Playwright 脚本，建议命令为：

```powershell
npm run e2e:static
```

本轮可以先用一次性 Playwright 脚本执行，确认问题清单后再决定是否沉淀为长期自动化测试。

## 5. 缺陷分级

- `P0`：核心流程不可用、密钥泄露、生成结果无法保存或严重误导用户。
- `P1`：主要流程可用但存在明显错误，例如目录授权不生效、历史无法恢复、批量重试逻辑错误。
- `P2`：功能可用但体验差，例如提示不清楚、布局阻碍使用、失败原因不明确。
- `P3`：轻微体验和文案优化，不影响完成任务。

## 6. 测试矩阵

### 6.1 首次打开与静态页面基础检查

1. 打开 `http://127.0.0.1:4174/`。
2. 检查页面标题、Logo、四个菜单：单图、批量、历史、设置。
3. 检查控制台是否有错误。
4. 检查设置页的版本切换链接：
   - 最新版：`https://kdb-wind.github.io/gpt-image-2-studio/`
   - 固定版：`/versions/v0.1.4/`
   - 最小 API 调用示例：GitHub README 对应锚点。

验收标准：页面无白屏，无启动错误，链接目标正确。

### 6.2 设置保存与刷新恢复

1. 进入设置页。
2. 填写 `Base URL`、`API key`、文字模型、生图模型。
3. 设置超时时间为 180 秒。
4. 保存配置。
5. 刷新页面。
6. 再次进入设置页，确认配置仍存在。
7. 检查 API key 是否只在浏览器本地状态中存在，不写入 HTML 文件。

验收标准：刷新后配置恢复；仓库文件不出现真实 key。

### 6.3 保存目录专项测试

这是本轮最高优先级。

1. 在 D 盘准备测试目录，例如：`D:\gpt-image-2-studio-e2e-output`。
2. 设置页点击“选择并授权目录”，选择该目录。
3. 点击“测试保存目录”。
4. 验证目录中是否出现测试文件，并且页面提示写入和读回成功。
5. 执行一次单图生成。
6. 检查生成图片实际是否保存到授权目录，而不是浏览器默认下载目录。
7. 刷新页面，进入历史记录，点击刚才图片。
8. 验证历史预览能否恢复。
9. 删除或移动图片，再次点击历史，验证错误提示是否准确。

需要记录：

- 页面显示的保存目录名称。
- 实际文件落点。
- 是否触发浏览器下载。
- 历史记录中的 `outputPath`。
- 控制台是否出现文件权限错误。

验收标准：授权目录通过测试后，生成图片应优先保存到授权目录；如果回退到浏览器下载，必须给出明确原因。

### 6.4 单图文生图

测试用例：

```text
生成一张暖色自然光的咖啡海报，画面干净，适合社交媒体封面。
```

步骤：

1. 单图页选择文生图。
2. 填写短提示词，生成图片。
3. 验证状态从生成中变为成功。
4. 验证结果预览显示图片。
5. 双击或点击放大，验证大图查看。
6. 验证历史新增记录。
7. 使用“基于此图修改”进入下一轮编辑草稿。

补充测试：

- 长提示词。
- 不同尺寸：1:1、9:16、16:9。
- 不同清晰度：1K、2K、4K。
- 质量：自动、低、中、高。
- 超时时间分别为 60、180、300 秒。

验收标准：成功图片能预览、保存、进入历史；失败时错误信息可读。

### 6.5 图生图兼容性

步骤：

1. 单图页切换到图生图。
2. 上传 1 张参考图。
3. 输入修改要求：

```text
保留主体轮廓，把背景改成浅色摄影棚风格，增加柔和自然光。
```

4. 生成图片。
5. 如果成功，验证预览、保存和历史。
6. 如果失败，记录供应商返回内容，并验证页面是否允许继续文生图。
7. 上传多张参考图，测试预览、删除、清空和上限。

验收标准：供应商不支持图生图时，不能造成页面卡死或污染历史；支持时应能正常进入保存和历史流程。

### 6.6 AI 批量任务规划

测试用例：

```text
为法国 / 日本 / 比利时 / 韩国 2026 世界杯制作宣传海报，每张海报使用该国家的母语文字，整体都是高质量体育商业海报风格。
```

步骤：

1. 批量页选择“同一提示词生成多张”。
2. 初始任务数量设为 3。
3. 开启“让 AI 自动调整任务数量”。
4. 点击“规划任务列表”。
5. 验证任务数量是否自动调整为 4。
6. 验证每个子任务是否分别对应法国、日本、比利时、韩国。
7. 手动删除一个子任务，验证任务列表和执行状态正常。

补充测试：

- 关闭“让 AI 自动调整任务数量”，确认始终按用户填写数量拆分。
- 使用水果、动物、商品、城市等非国家类任务，验证不是依赖固定词表。
- 文字模型返回异常或非 JSON 时，检查错误提示和恢复能力。

验收标准：AI 规划是通用能力；任务数量调整有提示；结果可编辑。

### 6.7 自定义多条提示词批量生成

步骤：

1. 批量页选择“自定义多条提示词”。
2. 设置任务数量为 5。
3. 输入 5 条完全不同提示词。
4. 点击“生成任务列表”。
5. 设置并发为 1，开始批量生成。
6. 验证任务按队列逐个执行。
7. 再设置并发为 3 或 5，验证同时运行数量符合配置。

验收标准：自定义提示词不被覆盖；并发数实际生效；完成后进入历史。

### 6.8 批量失败、暂停、继续与重试

测试方式：

- 使用错误模型名制造失败。
- 使用短超时时间制造超时。
- 使用并发较高配置测试限流。

步骤：

1. 批量开始后点击暂停。
2. 点击继续，验证未完成任务继续执行。
3. 对失败任务点击“重试该任务”。
4. 使用“重试失败项”。
5. 使用“继续未完成”。
6. 验证成功任务不被重复执行，失败任务状态更新正确。

验收标准：失败重试不会重跑已成功任务；暂停继续不会丢任务；错误提示保留在子任务上。

### 6.9 批量图生图

步骤：

1. 展开“批量参考图（图生图）”。
2. 上传 1 到 2 张全局参考图。
3. 生成 3 个子任务。
4. 验证每个任务都会带上全局参考图。
5. 展开全部子任务专属参考图。
6. 给某个子任务上传专属参考图。
7. 验证该任务实际使用全局参考图 + 专属参考图，或按 UI 勾选取消全局参考图。

验收标准：参考图作用域清晰；刷新前状态不丢；刷新后如果无法恢复参考图，提示必须清楚。

### 6.10 历史记录

步骤：

1. 完成至少 1 张单图和 1 个批量任务。
2. 进入历史页。
3. 验证按日期分组。
4. 展开批量历史，查看子任务标题、提示词和图片。
5. 点击单张历史图片，验证中间预览。
6. 刷新页面后重复检查。
7. 在授权目录存在时验证预览恢复。
8. 在文件被删除或移动后验证错误提示。

验收标准：历史记录可复用提示词；授权目录正确时能恢复预览；不能恢复时原因明确。

### 6.11 异常和边界

- 空提示词生成。
- API key 错误。
- Base URL 错误。
- 模型名错误。
- 供应商返回 429。
- 供应商返回 500。
- 供应商返回成功但没有图片数组。
- 网络断开或请求超时。
- localStorage 被禁用或访问失败。
- 在线页面和本地 `file://` 页面配置隔离。

验收标准：所有异常都能回到可操作状态，不出现页面崩溃。

## 7. Playwright 自动化建议

### 7.1 可自动化

- 页面启动与控制台错误检查。
- 设置填写、保存、刷新恢复。
- 文字模型测试。
- 文生图生成。
- AI 批量规划。
- 批量任务执行、暂停、继续、重试。
- 历史记录展示。
- 版本切换链接。

### 7.2 需要特别处理

- 目录授权依赖浏览器原生文件选择器，Playwright 不能像普通输入框一样直接填 `C:\...`。
- 可优先使用 Chromium 的 CDP / permission 授权能力测试部分流程。
- 如果自动化目录授权成本过高，需要保留一组人工复核步骤，并用 Playwright 记录授权前后的页面状态。

### 7.3 不建议自动化或只做抽样

- 大量 4K 生图。
- 高并发压测到供应商极限。
- 真实成本较高或生成时间不可控的长批次。

## 9. 本轮优先级

第一优先级：

- 保存目录授权是否真正生效。
- 生成图片是否仍落到浏览器默认下载目录。
- 历史预览是否能从授权目录恢复。

第二优先级：

- 单图文生图完整链路。
- 批量生图、AI 拆分、失败重试。
- 图生图兼容性。

第三优先级：

- UI 文案是否误导。
- 版本切换和 GitHub 文档入口。
- 移动端和小屏幕可用性。

## 10. 完成标准

- 至少完成 1 次单图文生图成功。
- 至少完成 1 次批量生成成功。
- 至少完成 1 次 AI 拆分成功。
- 至少完成 1 次失败重试验证。
- 完成保存目录专项测试，并明确判断当前实现是否有 bug。
- 输出缺陷清单和下一阶段修复建议。

## 修复后保存目录人工复测

Playwright 普通脚本不能直接操作浏览器原生 `showDirectoryPicker()` 目录选择器，因此保存目录真实落点必须人工复测：

1. 使用 Chrome 或 Edge 打开本地预览或 GitHub Pages 页面。
2. 在 `C:\Users\<User>\Downloads` 下新建 `gpt-image-2-studio` 子目录，不要直接授权 Downloads 根目录。
3. 进入“设置”，点击“选择并授权目录”，选择该子目录。
4. 点击“测试保存目录”，确认测试图片可以写入并读回。
5. 执行一次真实文生图。
6. 确认图片实际出现在授权目录下，而不是浏览器默认 Downloads 根目录。
7. 刷新页面，进入历史，点击刚才的记录，确认可以恢复预览。
